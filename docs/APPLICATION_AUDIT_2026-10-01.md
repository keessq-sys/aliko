# Aliko Diamond Key application and production audit

Audit date: 1 October 2026. Source revision: `e2e07272656be5019d547d397a7415aa46ecf914` on `main`, repository `keessq-sys/aliko`.

## Assessment

The application renders the correct Aliko Diamond Key brand and has substantial frontend and Convex infrastructure. It is **not ready for unrestricted production onboarding, identity-document handling, or live payments**. The remaining work includes serious application defects, incomplete workflows, empty production collections, and missing operational configuration. Supplying credentials alone will not complete it. Earlier percentage estimates are not a reliable readiness measure and did not account for the defects below.

This audit inspected current source, installed authentication and deployment tooling, GitHub and Cloudflare read-only configuration, production Convex public queries, the live homepage, and local automated checks. No test customer, administrator, payment, identity submission, or restore was created in production. Browser automation became intermittent after the homepage; authenticated dashboard behavior was inspected in source, not certified through a signed-in production session. Findings distinguish observed configuration, source defects, and unverified operational controls.

## Critical release blockers

### C1 — A public sign-up can select a privileged role

Evidence: `convex/auth.ts:26` copies `params.role` into the user record, accepting `ADMIN`, `AGENT`, and `ESTATE_MANAGER`. Installed `@convex-dev/auth` Password code calls the configured profile with caller-supplied parameters and passes that profile to `createAccount` during `signUp`. No server allowlist or administrator approval is present in that path.

Impact: A caller can obtain a privileged identity without going through the visible registration choices or administrative approval. Signed JWT verification does not help when the server itself creates an unauthorized administrator role. This was established from code; no exploit account was created.

Required: Force public sign-up to a permitted customer role. Make privileged provisioning an authenticated internal/admin operation, record an audit event, and add backend tests proving submitted role fields cannot grant privileges. Review any existing privileged accounts before launch.

### C2 — The staging restore helper can select production

Evidence: `scripts/restore-convex-staging.mjs:9` rejects only the literal names `prod` and `production`. It invokes import with `--replace-all --yes` and inherited environment. The installed Convex tooling states that a deployment key selects its deployment even when deployment-selection flags are supplied; the read-only environment command during this audit printed that warning. The local deployment configuration still selects production through a deploy key.

Impact: A purported staging rehearsal can replace production data. Actual production deployment names or qualified references are not rejected. This script must not be used for restore rehearsal in its present form.

Required: Use separate staging credentials and a clean environment, positively verify resolved target URL/project/deployment identity against an allowlist, reject production identity regardless of alias, and require an independently verified target before destructive import. Add tests for production keys, aliases, and mismatched targets. No import was run.

## Reliability, storage and frontend gaps

1. **Subscription cleanup and error states:** `src/lib/convex/queries.ts:23` ignores the unsubscribe returned by onUpdate and does not bind it to the store lifecycle. Navigation/filter-created stores retain subscriptions. Query failures only log a warning and can leave the UI indefinitely in loading/empty state. Add cleanup, typed error state and visible retry behavior.
2. **R2 orphan cleanup pagination:** maintenance lists the first 100 objects every run (`src/routes/api/media/maintenance/+server.ts:21`). It returns `more` but never a cursor; worker performs one call. Objects beyond an unchanged first page may never be considered. Use resumable cursor scanning and record progress/completion.
3. **Manual media cleanup authorization:** maintenance depends on locals.user for admin authorization, but `hooks.server.ts` resolves it for upload and dashboard routes, not `/api/media/maintenance`. A normal cookie-authenticated admin therefore receives 403. Authenticate that route explicitly; scheduled-secret authorization is a separate working path.
4. **Media deletion and access state:** R2 GET directly fetches a key without checking registered/deleted/quarantine status. DELETE removes the object before recording the Convex mutation; partial failure can leave inconsistent metadata/audit. Gallery references and long-lived cached images are not invalidated. Define public-published vs private/quarantined access, durable deletion state and reference cleanup.
5. **Scanning coverage/recovery:** Convex scanning is configured only for document purposes, not property images. Missing scanner credentials leave documents PENDING_SCAN indefinitely. The direct scheduled action has no durable retry/dead-letter path for scanner outages. R2 upload does not call the scanner. Configure a real scanner and exercise clean/infected/unavailable results on all relevant storage paths.
6. **Unbounded reads:** public listProperties collects then slices; approved agents, applications, services, site visits and several dashboard queries collect potentially growing collections. Limits after collect do not bound database work. Add appropriate indexes, bounded pagination and server-side filtering; counts capped at 10,000 are not exact at larger scale.
7. **Marketing/demo content:** homepage still renders StatsStrip's 1,247 listings, 86 agents, ₦12B and 98%; PropertyTypes, ExploreLocations, DualCTABanner and hero contain further fixed counts. Hero's “Maitama Luxury Villa” uses a random skyline picture from picsum, not that property. Signature developments are fixed marketing labels, not authoritative project records. Replace these with approved live content or accurate empty states. Testimonials component remains in source but is not mounted on the homepage; that is different from a live testimonial defect.
8. **Claim verification:** “zero fraud”, “government verified”, guaranteed returns/title checks and 15-year history are visible claims. No audit evidence substantiates them. Obtain business/legal approval and align wording with actual verification and payment behavior.
9. **Accessibility/theme:** compiler reports no accessibility warnings and smoke tests include a mobile layout; neither certifies contrast, keyboard use, screen-reader journeys, every modal, or all dashboards in both themes. Run a route/theme/viewport matrix with measured contrast and keyboard testing. The live logo is correct; do not classify it as missing.
10. **Media catalogue status:** local supplied assets exist under `static/Frontend UI Images`; ADK logo and city/map assets also exist. Image credits are documented. This audit does not certify every photo's subject, licence attribution, or its mapping to each gallery. Validate source assets individually and check all galleries for broken images, publication/ownership and approved categories.

## Test and release completion plan

1. Fix C1/C2 and all private-data authorization paths first. Write direct backend role/ownership tests; frontend route redirects cannot certify these controls.
2. Restore parity between frontend services and backend records; seed approved listings, plots, projects and agents in a genuinely isolated staging deployment. Never introduce fake “verified” production records just to make a test pass.
3. Complete onboarding role/account linking, publication approval, attachment ownership, sanitized storage, durable notifications and the signature/allocation workflow.
4. Protect delivery and isolate environments/storage. Make full relevant tests required in CI. Update property tests to use deterministic staging fixtures and separately assert the empty catalogue; current detail tests only check a title/main element and can pass a missing-record view.
5. Activate provider sandbox credentials and certify success, cancellation, failure, timeouts, duplicate callbacks, refund uncertainty, settlement mismatches, scanner outages and identity failure/expiry. Seven skipped tests mean untested coverage, not successful integration.
6. Configure monitoring, administrator identity controls, backups, recovery and approved legal/operational ownership; collect execution evidence.
7. Perform authenticated client/agent/manager/admin journeys and full desktop/mobile/light/dark accessibility checks before declaring production readiness.

A production readiness decision should be based on closure of these blockers and recorded acceptance evidence. A numerical completion percentage cannot compensate for a privilege-escalation path, public private-data queries, or an unsafe recovery script.
